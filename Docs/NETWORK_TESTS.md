# Ручная проверка серверного actor probe

Статус: **не выполнена**. DLL-сборка и статический анализ не подтверждают репликацию.
Нужна полная Crysis Wars 1.5, один dedicated и два отдельных клиента.
Сначала одинаковая архитектура/версия и экспериментальный WarsBots на всех трёх
процессах; совместимость обычного клиента проверять отдельным прогоном.

## Подготовка

Собрать `Scripts/Build-WarsBots.ps1 -ExperimentalSpawner`. Установить содержимое
staging `build/release-bin64-probe/Mods/WarsBots` по BUILD: только WarsBots.dll в
Bin64, info.xml, logo.jpg и LICENSE.txt. Не копировать CMakeFiles/исходники.
Для GOG без Bin32 использовать x64. Разрядность DLL и процесса обязана совпадать.

Из каталога установленной игры запустить:

```powershell
.\Bin64\CrysisWarsDedicatedServer.exe -mod WarsBots
```

Настроить IA и выбрать действительно установленную IA-карту штатным способом
(`sv_gamerules InstantAction`, затем `map multiplayer/ia/<имя_установленной_карты>`).
Подключить первого клиента через LAN/direct connect. В серверном журнале должны
быть initialization log и `Experimental spawner enabled`. В обычной OFF-сборке
команд `wb_probe_*` быть не должно.

## Основной сценарий

1. До загрузки карты выполнить `wb_probe_spawn 0 0 0`: ожидается отказ без сущности.
2. После загрузки и входа первого человека выбрать свободную видимую точку карты.
   Выполнить **на серверной консоли** `wb_probe_spawn X Y Z`, заменив X/Y/Z реальными
   мировыми координатами (метры, точка для дробной части). `0 0 0` не является
   универсальной точкой появления. Не ставить актёра внутрь игрока, геометрии или воды.
3. Сохранить `Probe created EntityId=...` и `wb_probe_status`. Ожидается channelId=0,
   IsPlayer=0 и `match participant=NO`. Здоровье/physics/inventory — диагностические
   данные, а не искусственно выставленные признаки успеха. Null CreateActor — отказ.
4. Первым клиентом проверить наличие модели в нужной точке. Сохранить скриншот и
   клиентский журнал. Наличие серверного EntityId не заменяет этот шаг. На этом этапе
   нет RevivePlayer: если модель/физика не готовы, зафиксировать это как результат
   эксперимента, не маскировать включением AI или выдуманного канала.
5. Только теперь подключить второго клиента. Проверить ту же сущность и позицию.
   Подключить наблюдателя/переподключить клиента ещё раз. Серверный статус не доказывает
   наличие локальной сущности у клиента; клиентский wb_probe_status не владеет репликой.
6. Повторный `wb_probe_spawn X Y Z` должен отказать. На клиентском процессе команда
   создания должна отказать; удаление там не должно менять серверную сущность.
7. `wb_probe_remove`: ожидать DONE/removal log, исчезновение у обоих клиентов и
   `No live owned probe` на сервере. Повторное удаление безопасно. Обычные игроки
   остаются подключёнными и управляемыми.
8. Повторно создать WarsBot_01: новый/повторно выделенный EntityId допустим, предыдущая
   сущность отсутствует. Выполнить минимум 20 циклов spawn/remove. Сравнить число
   сущностей/актёров и память после прогрева; один стабильный RSS сам по себе не
   доказывает отсутствие утечек. При доступном отладчике проверить heap и warnings.

## Жизненный цикл и отрицательные проверки

- Spawn с недостающими аргументами, NaN, Inf, мусором и координатой за ±1000000
  должен показать usage без создания. Существующую чужую сущность WarsBot_01 не удалять:
  конфликт имени должен блокировать создание.
- С активным probe: restart матча, переход на другую карту, unload/disconnect и
  штатный shutdown сервера. После каждого перехода старый EntityId не должен
  удерживаться менеджером или ошибочно удалять новую сущность с переиспользованным ID.
- При внешнем удалении probe движком ожидается ENTITY_EVENT_DONE и сброс владельца.
  Если removal veto/pending — повторный spawn не выполнять до выяснения причины.
- Не стрелять и не начислять очки в основном прогоне: это ещё не IA-игрок.
  Отдельный диагностический прогон повреждения проводить под отладчиком — stock Lua
  может ожидать player channel; это остаётся ограничением, а не реализованной функцией.
- Повторить пассивный probe на PS без покупок/захвата. Проверить отсутствие изменений
  команд и Prestige Points реальных игроков.
- Затем повторить с немодифицированным клиентом и явно записать совместимость/отказ.

## Протокол результата

Для каждого прогона записать SHA256 DLL, конфигурацию ON/OFF, разрядность, версию
игры/launcher, карту, координаты, число игроков, логи сервера/обоих клиентов,
момент позднего подключения, результаты каждого шага и ошибки. Исходы:
`PASS`, `FAIL` с точным симптомом либо `NOT RUN`. Не объединять успешную сборку,
создание на сервере, видимость первого клиента и late join в один статус.
